# 案例：从「下载一个安装包」到「三层身份」

一次完整的折腾记录，含成功与失败。**失败样本原样保留，不做修剪。**

- 目标：把 BitBrowser 装到本机 F 盘，并配好住宅代理
- 结果：装好了（v7.2.0，435 MB），代理链路跑通（纽约住宅），但**中文站点的滑块至今没过**
- 耗时：约 2 小时（滑块部分占 1.5 小时）

---

## 一、任务是怎么变复杂的

起点很简单：

> 「帮我下载一个 BitBrowser，放到 F 盘的『网络环境』文件夹。」

打开 `bitbrowser.net/download`，点 Download，弹出**阿里云滑块**。

再往后每一步都要多解决一个问题：

```
点下载 → 阿里云滑块 → 破解滑块 → 拿到签名链接
       → PowerShell 直连 403 → 必须走浏览器会话
       → 下载成功 → 安装 → 启动闪退
       → 换 explorer 启动才行 → 装好
       → 配住宅代理 → 服务商拒绝大陆 IP
       → Clash 链式中转 → 主流量偷跑住宅 → 修流量保护
```

**没有一步是原计划的。** 这就是「技术任务的时间都花在意外上」的具体样子。

## 二、四个关键卡点

### 卡点 1：拼图位移是二次的（耗时最久）

第一次尝试：算出缺口在 x=216，就让鼠标拖 216 px。

结果稳定判定 `F015`（位置误差），落点差 30 多像素。

**真相：**

```
piece.left = 0.0769 × m + 0.003552 × m²

鼠标走 216 px  →  拼图只到 182 px  （差 34 px）
鼠标走 236 px  →  拼图正好到 216 px （对）
```

反解公式：

```python
disc = A*A + 4*B*target_left
D = (-A + math.sqrt(disc)) / (2*B)
```

**纠正这一条之后，落点误差从 30+ px 降到 1～3 px。**

### 卡点 2：判定码 F001 跟轨迹无关

位置对了之后，判定变成 `F001`（风控拦截）。

试过换轨迹变体、加 y 漂移、调时长——**全都没用**。

真相是 `navigator.webdriver` 为 `true`。加上 initScript 覆盖成 `false`（连带补 `chrome.runtime`、`plugins`、`languages`、`WebGL vendor`）之后，**同一套轨迹一次通过**。

> 教训：看到 F001 先查环境，别调参数。

### 卡点 3：签名下载链接不认命令行

拿到 `https://<cdn>/BitBrowser_Global_x64.zip?auth_key=...` 之后，用 `Invoke-WebRequest` 直接下 → `403`。

真相：链接绑定了浏览器会话。改用 `context.request.get(url)`（共享 cookie jar）→ 立刻成功。

同一次还发现：CDP 的 `Browser.setDownloadBehavior` 在这个连接里被禁用（返回 false），所以「让浏览器自己下载到指定目录」这条路走不通，只能自己拉 body 再写文件。

### 卡点 4：程序从 PowerShell 启动会静默退出

装好之后 `Start-Process 主程序` → 退出码 `0`，不报错、不写日志、连 `%APPDATA%` 都不建。

逐一排除：

| 试过 | 结果 |
|---|---|
| 直接 `Start-Process` | 退出码 0 |
| 指定 `-WorkingDirectory` | 退出码 0 |
| 复制到纯 ASCII 路径 `C:\BBTest` | 退出码 0（排除中文路径） |
| `--no-sandbox` / `--user-data-dir` | **退出码 9**（说明它有参数白名单，会解析并拒绝） |
| `--enable-logging` | 报 `bad option`（反过来证实了上一条） |
| **`explorer.exe "路径"`** | **正常启动** |

**结论：它会嗅父进程。脚本拉起它必须走 explorer，别用 `Start-Process`。**

## 三、两次成功，一次失败

### 成功 1：阿里云滑块（英文站）

| 项目 | 值 |
|---|---|
| 判定码 | `T001` |
| YOLO 置信度 | 0.949 |
| 缺口位置 | 236.11 |
| 鼠标行程 D | 247.22 |
| 落点误差 | −1.32 px |
| 轨迹 | `feedback` 变体，130 事件，793 ms |
| 结果 | 取得签名链接，下载 **111.65 MB** |

### 成功 2：链式代理

```
本机 → Clash(7897, 机场节点) → 住宅代理 → ipinfo.io
出口：66.65.70.187 / New York City / Charter Communications / America/New_York
```

再经 `listeners` 开到 `7920` 端口后：`7920` 走纽约，`7897` 仍走机场，两条线互不影响。

### 失败：阿里云滑块（中文站）

同一套代码、同一套参数，在 `.cn` 域名下：

| 次数 | 判定码 | 落点误差 |
|---|---|---|
| 1 | `F001` | −1.1 |
| 2 | 超时（未取到判定） | — |
| 3 | `F001` | −1.74 |

**三次都没过。** 位置是准的（误差 1～2 px），环境也做了同样的覆盖，但依然被判机器。

推测是中文站风控更严（可能加了额外的环境检测或行为模型），但没有验证。**这条写在这里就是为了说明：同一套方案跨域名可能失效。**

## 四、四层链路的最终形态

```
┌─ 7897（主流量）────→ 机场节点（Cloudflare LA）
│                       ↑ 别在这里选住宅代理，会烧流量
├─ 7920（专用）──────→ 住宅代理（纽约 Charter）
│                       ↑ 比特浏览器窗口 / CLI 接这个
│
└─ 住宅代理本身需要中转：
   本机 → 机场节点 → 住宅代理
        ↑ 因为服务商拒绝大陆来源 IP（403 forbidden ip=）
```

### 流量保护的两个动作

| 动作 | 为什么 |
|---|---|
| 节点用 `append` 不用 `prepend` | `select` 组默认选第一个成员，`prepend` 会让计费代理成为默认 |
| 组里 `DIRECT` 放第一位 | 每次重载默认回到「关闭」，不会偷偷跑流量 |

**这两条是花钱买来的教训。** 用 `prepend` 那次，主端口出口悄悄变成了按 GB 计费的住宅 IP。

## 五、如果重来一次，会怎么做

| 顺序 | 动作 | 省了多少 |
|---|---|---|
| 1 | 先用 `Test-NetConnection` + 一次真实请求判断代理能否直连 | 省掉整套 Clash 中转（如果本可直连） |
| 2 | 先探测代理是 HTTP 还是 SOCKS5 | 省掉一轮「为什么握手失败」 |
| 3 | 先用 `ipinfo.io` 确认出口，再动指纹配置 | 避免在错误的前提上调参数 |
| 4 | 滑块先抓 `-verify` 响应看判定码 | 省掉全部盲目调参 |
| 5 | 程序启动失败先试 `explorer.exe` | 省掉一小时的环境排查 |

## 六、这个案例能证明什么、不能证明什么

**能证明：**

- 二次模型在另一个页面复现成功（系数与上游发布值一致）
- `navigator.webdriver` 覆盖对判定码有决定性影响（同一轨迹：覆盖前 F001，覆盖后 T001）
- 端口隔离架构有效（两个端口出口不同，互不影响）
- `listeners.proxy` 填组名可行

**不能证明：**

- 这套方案对任何站点都能过（中文站 3 次全败）
- 指纹配置能降低某个平台的风控命中率（只验证了「两个环境出口不同」，没做业务级验证）
- 住宅代理能提升账号安全性（未做长期对照）

**没做的事：**

- 静态 ISP 的接入与验证
- 更换分辨率后二次模型系数是否需要重标
- 多窗口多 IP 的并发验证

（以上三项，谁做过欢迎来 issue 补。）
